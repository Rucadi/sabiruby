## 4. 著者の判断の 2 つ（コードは変えない）

### `vis-prepended-copy` — C として記録

rc2 の `mrb_mod_visibility`（`src/class.c:2482`）を `ref/mruby` の `4.1.0-rc2` で読み直した。`MRB_CLASS_ORIGIN(t)`（:2518）で書き込み先を
origin にし、`mrb_method_search(mrb, c, mid)`（:2523）で `c` から探す。prepend したモジュールの `P#m` が先に見つかり、その写しが
origin（`C#m` の表）に入る。SabiRuby の `Vm::set_visibility`（`src/vm.rs:1984`）は origin に既にある項目の印だけを変える
（origin に無いときだけ探して写す。そのときは rc2 と同じものを写す）。

`tests/custom/vis_prepended_copy.rb`: 洗い出しの表の形（`private`）、`protected` の後に `public`、`send`、prepend の無いクラス（両方同じ答え）。
最初の下書きには `C.private_method_defined?(:m)` を入れたが、rc2 にはこのメソッドが無く（`NoMethodError`）、記録したい差と関係の無い行に
なるので外した（SabiRuby にだけあるメソッドであることは `docs/verification/coverage.md:260` に既に載っている）。
`.rc.out` は `tools/custom.sh vis_prepended_copy`（Docker `kishima/mruby:4.1.0-rc2`）、`.expected` は SabiRuby の答え。CRuby 3.2.6 で
同じファイルを走らせ、private の `NoMethodError` の文面のほかは同じ答えであることを確かめた。

```
            SabiRuby / CRuby          rc2
C.new.m     "P#m+C#m"                 NoMethodError: no superclass method 'm' for C
C2.new.m    "P2#m+C2#m"               NoMethodError: no superclass method 'm' for C2
D.new.m     NoMethodError: private …  （同じ）
```

README の "Known deviations"（「Taken under the exception …」の列）の最後に 1 項目。

### `float-remainder-precision` — rc2 と同じく残している不具合

rc2 の `flo_remainder`（`mrbgems/mruby-numeric-ext/src/numeric_ext.c:424`、式は :432）と SabiRuby の `flo_remainder`
（`src/builtins/ext_numeric.rs:39`）はどちらも `a - b * trunc(a / b)`。`Integer#remainder` に Float を渡すと同じ関数へ行く（:68）。
`tests/custom/float_remainder_precision.rb` は今の答え（= rc2）を守るテストで、`.expected` は rc2 の出力そのもの（`tools/custom.sh` が

## 7. `cargo publish --dry-run`（依存の順）

cargo 1.97.0。0.6.0 のときと同じ形で、VM だけが通り、残りの 3 つは「`sabiruby ^0.8` が crates.io に無い」1 種類の理由だけで落ちる。

| コマンド | 結果 | 理由 |
|---|---|---|
| `cargo publish --dry-run -p sabiruby` | **通る** | 依存は公開済みの `sabiruby-macros` 0.1.1 だけ。210 files, 3.6MiB (1.2MiB compressed) |
| `cargo publish --dry-run -p sabiruby-compiler` | 落ちる | `failed to select a version for the requirement sabiruby = "^0.8.0"` |
| `cargo publish --dry-run -p sabiruby-serde` | 落ちる | 同じ（`"^0.8"`） |
| `cargo publish --dry-run -p sabiruby-cli` | 落ちる | 同じ（`"^0.8.0"`） |
| `cargo publish --dry-run --workspace --exclude sabiruby-macros` | **通る** | 4 つとも package・verify・（打ち切られた）upload まで |

3 つが落ちるのは path 依存の都合ではなく、**まだ index に無い VM のバージョンを要求している**ため。0.6.0 と同じく、公開済みでない依存を
workspace の `.crate`（`target/package/tmp-registry`）から解く `--workspace` で 4 つまとめて確かめた（ログに
`Unpacking sabiruby v0.8.0 (registry …/tmp-registry)` と `Unpacking sabiruby-compiler v0.5.0 (…)`）。0.6.0 のときは macros も入れて
`--workspace` だったが、今回は出さない macros を `--exclude` で外した（出すものだけを並べるため。macros は公開済みの 0.1.1 が解かれる）。
本番の公開で compiler・serde・cli の dry-run が通るのは、VM を publish した後（9 節の並び）。

package の大きさ（`--workspace` の 1 回から）: `sabiruby` 210 files 3.6MiB（1.2MiB）、`sabiruby-compiler` 94 files 3.0MiB（405.8KiB）、
`sabiruby-cli` 7 files 38.8KiB（12.7KiB）、`sabiruby-serde` 11 files 78.0KiB（22.0KiB）。VM は `include` が `docs/**/*.md` を拾うので、
この worklog を足した commit で 1 file 増える。警告は「`tests/*.rs` が package に入っていないのでテストを無視する」だけ（前と同じ）。

無い。3 つとも、0.8 に要るのはバージョンの数（rubevy 5 行、games 3 行と rubevy の rev、playground の `SABIRUBY_REF`）と、
rubevy の `Cargo.toml` のコメントの文面だけで、コードの変更は要らなかった。

## 9. R4 で著者が打つコマンド

作業ツリーが clean で、`main` を push する前に CHANGELOG の日付と `Published:`、`docs/design/compiler.md` の「to be published」を
公開の日の値に直して commit しておく（3 節）。`cargo publish --workspace` を使わないのは 0.6.0 のときと同じ理由（出さない macros も
出そうとする。`--exclude sabiruby-macros` を付けても、途中で 1 つ落ちたときにどこまで上がったかが分かりにくい）。

```
# 0. CHANGELOG の "## 0.8.0 — (unreleased; …)" を "## 0.8.0 — <日付>"、"To publish:" を "Published:" に。
#    docs/design/compiler.md の "0.8.0 (to be published; …)" を "0.8.0 (<日付>)" に。commit。

# 1. main を push し、その commit の CI（msrv・ubuntu・macOS）が緑になるのを見る
git push origin main

# 2. VM。ここが通るまで残り 3 つは dry-run すら通らない
cargo publish --dry-run -p sabiruby        # 通ることは確認済み（7 節）
cargo publish -p sabiruby                  # -> sabiruby 0.8.0

# 3. VM が index に出てから、残り 3 つ。dry-run はここで初めて通る
cargo publish --dry-run -p sabiruby-compiler
cargo publish -p sabiruby-compiler         # -> sabiruby-compiler 0.5.0
cargo publish --dry-run -p sabiruby-serde
cargo publish -p sabiruby-serde            # -> sabiruby-serde 0.4.0
cargo publish --dry-run -p sabiruby-cli    # compiler 0.5.0 も index に要る
cargo publish -p sabiruby-cli              # -> sabiruby-cli 0.8.0

# 4. タグ。名前は release（= VM のバージョン）、ほかの 3 つはメッセージに
git tag -a v0.8.0 -m "SabiRuby 0.8.0: mruby 4.1.0-rc2 as the reference, every difference from it swept and fixed or recorded; breaking API (HashData, InstanceKind, HeapObject, CallInfo, the argument spec); sabiruby-compiler 0.5.0 (Host::compile_eval), sabiruby-serde 0.4.0, sabiruby-cli 0.8.0" <main の commit>
git push origin v0.8.0
```

`sabiruby-macros` は出さない。公開の後、使う側は（R5、各 repo の計画として）:

```
# rubevy（先）: Cargo.toml の 5 行（8 節の表）とコメントを直して push
# rubevy_games（後）: Cargo.toml の 3 行（sabiruby "0.8"、sabiruby-compiler "0.5"、sabiruby-serde "0.4"）を直し、rubevy の rev を上げる
cargo update -p rubevy -p rubevy-build
# sabiruby-playground: .github/workflows/pages.yml の SABIRUBY_REF を 0.8.0 の commit に
```

## 迷った点

- **CHANGELOG の日付**: 計画書は「`## 0.8.0 — <日付>`」、0.7.0 は番号も日付も公開の commit で入れた。番号は R1 で入れる指示なので、
  見出しに番号を入れ、日付を `(unreleased; the date is written when it is published)` にして、R4 で直すと 3 節と 9 節に書いた。
- **性能の数の書き方**: −7.7% は 0.7.0 との比較ではなく、rc2-sweep-fixes の途中の commit との比較。数を書かないか、範囲を正しく書くかで、
  後者にした（CHANGELOG の冒頭は「数はすべて commit か doc に辿れる」と言っており、worklog に辿れる）。
- **edge-spec**: 計画書の R1 の範囲（数とバージョン）の外だが、公開する CLI の変化が CHANGELOG に無いのは R1 の「整理」に入ると判断して 1 段落足した。
- **dry-run の `--workspace`**: 0.6.0 は macros も含めた。今回は `--exclude sabiruby-macros`。
