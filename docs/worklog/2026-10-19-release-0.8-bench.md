# 2026-10-19 — 0.8.0 の候補の計測（計画 R3、著者の合図「ベンチしてもいいよ」の後）

計画は [`../plans/release-0.8-plan.md`](../plans/release-0.8-plan.md) の R3。測ったもの: **変更前** = tag `v0.7.0`
（`4d3036a`）、**変更後** = main `e7a3381`（R1・R2 の後、0.8.0 の候補）。やり方は 0.7.0 のとき
（[`2026-09-27-release-0.7-bench.md`](2026-09-27-release-0.7-bench.md)）に合わせた。結果の TSV は
`bench/results/release-0.8/`。

## 取り方

- スクラッチパッドに `git worktree add --detach` で 2 つの木を作り、別々の `CARGO_TARGET_DIR` で
  `cargo build --release -p sabiruby-cli`。md5 は変更前 `36cad7f6…`、変更後 `802f6e50…` で別物。`--version` も
  `sabiruby 0.7.0` と `sabiruby 0.8.0`。バイナリを写してから worktree は `git worktree remove` で消した。
- `tools/bench_ab.sh`、5 回 × 巡、`--core 2`。回ごとに A と B のどちらが先かを入れ替える（スクリプトの既定）うえに、
  巡ごとにも A と B を入れ替えた（名前が `r` で終わる巡は A = 0.8.0、B = 0.7.0。表では向きを直してある）。
  数は各側の全巡の最速どうし。各組で A/B を 3 巡（`ab-1`、`ab-2r`、`ab-3`）、A/A（0.7.0 どうし）を 2 巡（`aa-1`、`aa-2`）。
  順は組ごとに aa-1 → ab-1 → ab-2r → aa-2 → ab-3。
- 巡の前に `vmstat 1 6` の後ろ 5 秒の idle の平均が 97% 以上になるのを待ち（全巡ですぐ通った、98〜99%）、
  `vmstat -t 10` を通して記録した（`bench/results/release-0.8/vmstat.log`、巡の始めと終わりは `rounds.log`）。
  24 スレッドの機械で 1 本のベンチが 1 コアを使うと idle は 95〜96% になる。それより下がった標本は 5 つ:
  `bench-ab-2r` の 01:49:32（82%）・01:49:42（89%）・01:52:39（79%）・01:53:10（91%）と、`bench-aa-2` の 02:03:42（90%）。
  どれも 10〜30 秒の一瞬で、`--core 2` の外の仕事。交互に測っているので両側に同じように掛かる。
  `pgrep -af "sabiruby|cargo|mruby"` で見たとき、ほかの VM の計測やビルドは動いていなかった（family-mruby の
  セッションの `docker logs` の待ちループが 2 秒おきに動いていただけ）。**02:17 から family-mruby の ESP32 のビルド
  （Docker）が始まった**が、そのときには 3 つの組の巡は全部終わっていた（02:13:23）。
- 3 つの組:
  - `bench/` の 27 本（そのまま `tools/bench_ab.sh`）。
  - `bench/micro-wait/` の 21 本。repo には `N = …` の 1 行を抜いた `.rb` しか無いので、
    [`2026-09-26-wait-anywhere.md`](2026-09-26-wait-anywhere.md) の「マイクロの `N`」の一覧の値を頭に足し、
    Docker の `kishima/mruby:4.1.0-rc2` の `mrbc` でスクラッチパッドにコンパイルした。
  - `bench/micro-tasks/` の 7 本（repo の `.mrb` をそのまま）。
  後の 2 つは、README にあるとおり `tools/bench_ab.sh` の写しを使った（変えたのは `cd` の先を repo に固定する行と、
  `DIR=bench` を `DIR=${BENCH_DIR:-bench}` にする行だけ）。`categories.tsv` は空のものを置いた（0.7.0 のときと同じく
  分類は `other`）。

## A/A と線

0.7.0 どうし、各組 2 巡。1 本ずつの最速どうしの差の最大は **タスク 3.1%（`t_sleep_1000`、70 ms のベンチ）、wait 1.9%、
`bench/` 4.8%（`vmo_objects`。これを除くと 1.6%）**。合計では A/A は −0.5%／+0.2%（タスク）、+0.0%／+0.2%（wait）、
−0.2%／+0.2%（`bench/`）。0.7.0 のとき（1.2%、1.8%、1.8%）より `t_sleep_1000` と `vmo_objects` が広い。
線は前と同じく「この最大を超え、全巡で同じ向き」。

## 命令の数（`--stats`）

0.7.0 と 0.8.0 のバイナリで 55 本を 1 回ずつ走らせ、`instructions:` と GC の回数を並べた
（`bench/results/release-0.8/insns.tsv`）。**命令の数は 55 本すべてで 1 命令も違わなかった。** 頼まれたときの見立ては
「挙動が変わったので同じではないはず」だったが、0.7.0 → 0.8.0 で変わった挙動（Hash の比べる順、文字列の式展開が `to_s`
を送る相手、`Array#index` などの `==`、定数の探し方、…）は、どれもネイティブの中か、ベンチが通らない枝の話で、
実行する命令の列を変えない。`src/mrblib/` の生成物も `v0.7.0` から変わっていない（`git diff --stat v0.7.0 e7a3381 -- src/mrblib`
が空）ので、Ruby で書かれたメソッドの命令も同じ。ベンチの `.mrb` は本家の `mrbc` が作ったもので、両方に同じものを渡している。
速くなったのは命令の数ではなく、1 命令あたりの時間。

GC の回数が違ったのは 3 本: `app_json_hash` 2301 → 2300、`bm_so_lists` 5 → 2、`m_array_new_block` 36 → 24。
ほかの 52 本は同じ。確保の仕方（キーワードの Hash の大きさなど）が変わった分と見ているが、1 本ずつは追っていない。

## 大きく変わったもの

どれも命令の数は同じ。0.7.0 の後の worklog に、その段で測った数がある（ここで改めて切り分けてはいない）:

- `vmo_dispatch` −20.2%、`vmo_arith` −16.1%、`loop_while_add` −11.2%、`loop_if_branch` −9.9%、`vm_optimization_bench` −11.5%:
  rc2-sweep-fixes Y7 の `OP_ADDILV`／`OP_SUBILV` の Integer と Float の速い道（`83ede9c`。その段の A/B で
  instruction loop −12.0%、`loop_while_add` −13.3%、`vmo_dispatch` −18.9%、[`2026-10-18-rc2-sweep-fixes.md`](2026-10-18-rc2-sweep-fixes.md)
  の Y7「性能」）。Y8b の `OP_DIV` の速い道は戻したので 0.8.0 には入っていない。
- `call_kwargs` −17.5%、`app_json_hash` −13.7%: キーワードの Hash を `mrb_hash_new_capa` の大きさで作り、AR の探索で
  `hash` を聞かなくなった分と見ている（[`2026-10-16-follow-master.md`](2026-10-16-follow-master.md) で `call_kwargs` −12.3／−5.2／−12.9、
  `app_json_hash` −6.3／−8.3／−3.7）。
- `m_hash_miss` −15.4%、`m_hash_hit` −12.6%、`m_hash_default_proc` −9.9%: Hash を本家の順で比べるようにした書き直し
  （16 本までは `hash` を聞かずに並びを見る）と上の AR の探索の分と見ている（このベンチでの切り分けはしていない）。
- `m_public_send` −12.7%、`m_sort_block` −12.3%、`m_method_call` −9.3%、`call_args` −8.4%: rc2-sweep-fixes Y8a の
  「可視性をメソッドキャッシュに持たせる」（`0313eaa`、その段の A/B で 27 本の合計 −3.7%、`call_args` −8.3%、`bm_ao_render` −8.5%、
  `app_robot` −6.2%）。明示の受け手の SEND が多いものほど効く。

0.7.0 のときに残っていた「線を超えて遅い」もの（`m_sort_plain` +9%、`m_new_plain` +2.9%）は、今回は
`m_sort_plain` −6.7%、`m_new_plain` −4.0% で、0.7.0 より速い。

## 遅くなったもの: `vmo_objects` +2.6%

27 本でただ 1 本、0.8.0 が遅い側に出た。巡ごとに +2.8、+5.9、+0.3 で、全巡同じ向き。ただしこのベンチ自身の A/A が
+4.8%／−3.2% と組の中で一番広く（ほかの 26 本の A/A は 1.6% 以内）、0.7.0 のときも A/A 1.8% と広い側だった。
最速と中央値の開きも大きい（0.7.0 の `ab-2r` で 574.5／605.8 ms）。命令の数（30,349,025）と GC の回数（771）は同じ。

「1 本が A/A の幅を大きく超えた」には当たらないが、全巡同じ向きだったので、`vmo_objects` だけをもう 6 巡取った
（`bench/results/release-0.8/objx-*.tsv`、02:14〜02:16、idle 99%）: A/B は −0.9、+3.2、+1.2、+1.1%（`r` の巡は向きを直した値）、
A/A は −1.5、−4.8%。全巡の最速どうしでは 0.7.0 568.2 ms → 0.8.0 566.8 ms（−0.2%）。合わせると、0.8.0 がわずかに遅い側に
寄って見えるが A/A の幅の中で、遅くなったとは言えない。原因の切り分けはしていない（判断の線に当たらないため）。
この後もう 2 巡（`objx-ab-7`、`objx-ab-8r`）を取ったが、02:17 から ESP32 のビルドが始まって中央値が 1382 ms まで
乱れたので捨てた（repo には置いていない）。

## 本家比（README の 2.57x の取り直し）

README の 2.57x は `docs/verification/bench.md` の「The new baseline（`bench/results/96221fb.tsv`）」で、`tools/bench.sh --core 2`
（best of 5、本家は Docker の `kishima/mruby:4.1.0-rc2` の中で `date +%s%N` で挟む）で取ったもの。同じ手順で取り直した:
`SABIRUBY_BIN=<0.8.0 のバイナリ> tools/bench.sh --core 2 --label ref-e7a3381`。`tools/bench.sh` は始めに `../../ref/mruby` の
`benchmark/*.rb` を `bench/src/` に写し、Docker の `mrbc` で `bench/*.mrb` を作り直すが、`ref/mruby` は `c17ffcc24`
（4.1.0RC2）で写すファイルは `bench/src/` と同じ、作り直した `.mrb` も repo のものとバイト単位で同じ（`git status` が
きれいなまま）。`bm_app_lc_fizzbuzz.rb` の `mrbc` のエラー（`nesting too deep`）は 27 本に入っていないファイルのもので、前からある。

1 回目（02:19〜02:25、`ref-e7a3381-try1.tsv`）は捨てた。02:21〜02:22 に idle が 76〜90% に落ちた時間があり、SabiRuby 側の
